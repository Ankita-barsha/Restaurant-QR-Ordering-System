# Deploying

Two pieces go to two places: the **API + PostgreSQL** to Render, the **client**
to Vercel. Both have a free tier that is enough to demo this.

There is a chicken-and-egg problem — the API needs the client's URL for CORS,
and the client needs the API's URL. The order below resolves it: deploy the API
first with a placeholder, deploy the client, then correct the API.

---

## 1. Push the repository

```bash
git push -u origin main
```

Render and Vercel both deploy from GitHub, so this has to happen first.

---

## 2. API + database on Render

1. Go to **render.com → New → Blueprint** and pick this repository.
   Render reads [`render.yaml`](render.yaml) and creates both the web service
   and the PostgreSQL database.

2. It will ask for the values marked `sync: false`. Set them to:

   | Variable | Value for now |
   |---|---|
   | `CORS_ORIGIN` | `http://localhost:5173` — corrected in step 4 |
   | `QR_BASE_URL` | `http://localhost:5173` — corrected in step 4 |
   | `SEED_ADMIN_EMAIL` | your admin email |
   | `SEED_ADMIN_PASSWORD` | a strong password you choose |

   `JWT_SECRET` and `JWT_REFRESH_SECRET` are generated by Render. Do not set
   them by hand and do not change them later — rotating either signs every
   staff member out.

3. Wait for the first deploy. Migrations run automatically
   (`prisma migrate deploy`). Note the service URL, e.g.
   `https://restaurant-api.onrender.com`.

4. Seed the roles, permissions and admin account. In the Render dashboard open
   **Shell** on the service:

   ```bash
   npm run seed
   ```

   Add sample menu, tables and staff accounts too, if you want something to
   look at:

   ```bash
   npm run seed:demo
   ```

5. Check it is alive: `https://your-api.onrender.com/api/health`

---

## 3. Client on Vercel

1. **vercel.com → Add New → Project**, import the same repository.
2. Set **Root Directory** to `client`. Vercel reads
   [`client/vercel.json`](client/vercel.json) for the rest.
3. Add one environment variable:

   ```
   VITE_API_URL = https://your-api.onrender.com
   ```

   No trailing slash. This is baked into the bundle at build time, so changing
   it later requires a redeploy, not just a restart.

4. Deploy, and note the URL, e.g. `https://restaurant-qr.vercel.app`.

---

## 4. Point the API back at the client

In Render → Environment, correct both values to the Vercel URL:

```
CORS_ORIGIN  = https://restaurant-qr.vercel.app
QR_BASE_URL  = https://restaurant-qr.vercel.app
```

Save. Render restarts the service.

**Both matter, and they fail differently:**

- `CORS_ORIGIN` wrong → the browser blocks the login response. The API looks
  healthy in a terminal and completely broken in the app.
- `QR_BASE_URL` wrong → printed QR codes open the wrong site. Nothing errors;
  diners just land somewhere unexpected.

---

## 5. Verify

| Check | URL |
|---|---|
| API alive | `https://your-api.onrender.com/api/health` |
| Client loads | `https://your-client.vercel.app` |
| Menu is public | `https://your-client.vercel.app/menu` |
| Staff sign-in works | `https://your-client.vercel.app/login` |
| **Deep link survives refresh** | open a `/t/<token>` URL, then press reload |

That last one is the SPA rewrite doing its job. If it 404s, `vercel.json` was
not picked up — check the Root Directory is `client`.

Then sign in, open **Tables & QR**, and download a QR. It is rendered on demand
from the table's current token, so it always encodes the correct public URL.

---

## Known limits of the free tier

**Uploaded food images do not survive a restart.** Render's free filesystem is
ephemeral. QR codes are unaffected — they are regenerated on demand from the
table token, which is why `GET /api/tables/:id/qr.png` exists. Food photos are
the only thing lost.

To fix it properly, implement `StorageProvider` in
[`server/src/utils/storage.ts`](server/src/utils/storage.ts) for S3, Cloudinary
or R2 and swap the export at the bottom of that file. Nothing else changes —
no controller or service touches the filesystem directly.

**The free web service sleeps after inactivity.** The first request after a
quiet period takes 30–60 seconds. Fine for a demo, not for a real restaurant.

**The free database expires after 90 days.** Back it up or upgrade before then.
